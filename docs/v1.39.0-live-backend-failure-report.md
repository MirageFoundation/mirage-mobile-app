## Backend origin: facts versus hypotheses

References below are to the read-only local `mirage-node/web/backend` checkout; the remote deployed revision is unknown.

1. **Proven:** valid guest bootstrap fails even without a view or user address. Therefore neither feed aggregation nor user-only quota/follows/blocked sections is required to trigger this observed failure. Standalone node config, feed, communities and welcome statistics succeed. This is inconsistent with claiming a universal public API or total database outage; cached successes alone cannot prove full DB health.
2. **Strong lead:** chain config and parameters now return `node_catching_up`. `routes/public.py:3283-3284` directly gates parameters on `_is_catching_up()`. `public.py:4166-4167` similarly gates uncached chain config. `chain.py:219-256` defines readiness from indexer checkpoint, processed time, observed chain head and recent block time; it raises `IndexerUnavailable` for unreadable state rather than treating DB failure as catch-up.
3. **Exact error can be misleading:** bootstrap's required-section `except Exception` at `public.py:4664-4666` translates **every** exception to `indexer_unavailable`. The protected work includes tag parsing, `_build_node_config()`, and `_build_chain_config()` (`public.py:4650-4653`). This is not a PostgreSQL-only catch and does not establish DB outage.
4. **Concrete consistent catch-up path:** bootstrap's early guard at `public.py:4643-4644` permits anonymous requests when both config caches exist, without checking their age. `_build_chain_config()` checks its cache TTL (`public.py:4124-4125`), then raises `RuntimeError("node_catching_up")` if behind (`public.py:4127-4128`). If the chain cache exists but is stale, the anonymous request passes the first guard, the builder raises, and the broad required-section catch mislabels it as `indexer_unavailable`. Meanwhile standalone chain config correctly returns `node_catching_up`. This explains the observed combination without a total DB outage. **Hypothesis, not proven remote traceback:** cache state and deployed code were not inspected remotely.
5. **Other possibilities requiring evidence:** `_build_chain_config()` indexes required governance keys (`public.py:4132-4144`), so missing/mismatched parameter schema could raise KeyError under the same generic catch. `params.py:179-188` can raise IndexerUnavailable for uninitialized or failed-refresh parameter cache. Node-config runtime/model access (`public.py:4197-4201`) is another generic-catch source, though its standalone success makes a persistent node-config failure less likely. Different workers/cache state or deployed revision divergence remain possible. No particular missing column, field, or migration was proven.
6. The later `bootstrap.user.err` path (`public.py:4707-4721`) handles typed DB/backend exceptions, but no-view/no-address probes execute no user tasks and `_build_bootstrap_view` returns immediately. That makes the required-section path the more useful initial operator check.
